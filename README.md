# ServerCalc

Справочный каталог виртуальных серверов с подбором под задачу. Next.js App Router, данные из JSON, вся сборка статическая: 49 страниц, ни одного запроса к базе на отдаче

## Быстрый старт

```bash
npm install
npm run dev          # разработка, http://localhost:3000
npm run build        # сборка
npm run start        # прод-режим на собранном
npm run check        # проверка ограничений проекта на запущенном сайте
```

Node 20 или новее

## Как поменять домен и название

Всё в одном файле `data/site.json`. Поменяли `name`, `domain` и `url`, пересобрали, дальше подтянется везде: тайтлы, канонические адреса, sitemap, микроразметка, подвал, юридические страницы

Метка `utmSource` тоже здесь. Сейчас `servercalc`, как в стандарте меток

## Демо-режим и правило свежести

Сейчас сайт в демо-режиме: `data/taxonomy.json` → `meta.dataStatus: "demo"`. В этом режиме вверху висит честная плашка, а правило свежести не режет витрину, потому что демонстрационные цены не обязаны быть свежими

Когда парсер начнёт писать реальные цены, поставьте `meta.dataStatus: "live"`. После этого:

- плашка демо-режима исчезнет сама
- заработает правило: тариф с `verifiedAt` старше семи дней перестаёт показываться
- на странице провайдера вместо тарифов появится блок «цены на проверке»
- служебная плашка на политике конфиденциальности тоже исчезнет

Срок семь дней меняется в `data/site.json` → `staleAfterDays`, разово можно переопределить переменной окружения `SERVERCALC_STALE_DAYS`

Важно: сборка статическая, дата сравнения фиксируется в момент `npm run build`. Значит после каждого прогона парсера нужна пересборка, это одна команда и разумно повесить её на тот же cron

## Как опубликовать новость

Положить файл в `content/news/`, имя файла станет адресом. Всё, никакой админки

```markdown
---
title: "Заголовок. Кавычки обязательны, если внутри есть двоеточие"
date: 2026-08-05
rubric: novosti
description: "Одно предложение для превью и для поисковой выдачи"
author: Редакция ServerCalc
---

Текст в обычном markdown. Заголовки внутри через ##
```

Рубрики: `novosti` (что происходит на рынке), `obzory` (как выбирать), `ceny` (журнал изменений цен). После добавления файла нужна пересборка

Единственная ошибка, на которую легко наступить: двоеточие в заголовке без кавычек ломает разбор. Сборка от этого не падает, файл просто не попадёт в ленту, а в лог уйдёт предупреждение

## Как добавить провайдера или тариф

`data/providers.json`, минимальный набор полей:

```json
{
  "slug": "example",
  "name": "Example Cloud",
  "color": "#1a5fd0",
  "country": "RU",
  "affiliateStatus": "active",
  "url": "https://example.com/?aff=123",
  "site": "https://example.com",
  "geos": ["ru", "eu"],
  "tasks": ["sajt", "magazin"],
  "virtualization": ["KVM"],
  "features": { "panel": true, "ddos": true, "backup": true, "hourly": false, "testPeriod": false },
  "description": "…",
  "pros": ["…"],
  "cons": ["…"],
  "verifiedAt": "2026-08-05"
}
```

`affiliateStatus: "pending"` означает, что провайдер участвует в подборе, но ссылка на него обычная, без метки и без вознаграждения. Такие провайдеры нужны: без них сравнение выглядит неполным

`data/plans.json`, один тариф:

```json
{
  "id": "example-1",
  "providerSlug": "example",
  "name": "Старт",
  "cpu": 2, "ram": 4, "disk": 60,
  "diskType": "NVMe",
  "geo": "ru",
  "price": 690, "currency": "RUB", "priceRub": 690,
  "billing": "month",
  "ipv4": true,
  "verifiedAt": "2026-08-05",
  "dataStatus": "demo"
}
```

Страница провайдера, строки каталога, sitemap и микроразметка появятся сами

## Контракт для парсера

Парсер должен обновлять `data/plans.json` и трогать ровно три вещи у каждого тарифа: `priceRub`, `verifiedAt` и `dataStatus`. Дата ставится в день фактической сверки, а не в день запуска скрипта

Порядок работы, который планировался: парсер пишет JSON, кладёт расхождения цен в отдельный журнал, дальше запускается пересборка. Журнал расхождений это готовый материал для рубрики «изменения цен»

Поля, заведённые на вырост и пока пустые: `renewalPrice` (цена продления отдельно от промо), `setupFee`, `trafficTb`, `portSpeed`, `panelPrice`, `benchmark`, `stock`

## Партнёрские ссылки

Собираются только в `lib/utm.js`, руками нигде не пишутся. Стандарт метки:

```
utm_source=servercalc&utm_medium=referral&utm_campaign=<место>&utm_content=<провайдер или тариф>
```

Значения `utm_campaign`: `calculator`, `catalog`, `provider_page`, `providers_list`, `task_<slug>`, `geo_<slug>`. Это даст разрез по страницам в кабинетах партнёрок и покажет, какие страницы реально приносят деньги

Отдельный случай UltaHost: ссылка вида `https://ultahost.com/#MakeBiz`, метка обязана вставляться ДО решётки, иначе реферальный идентификатор перестаёт работать. Это обеспечено конструктором URL и проверяется в `npm run check`

Все партнёрские ссылки получают `rel="sponsored nofollow noopener"` и `target="_blank"`. Провайдеры без партнёрства отдают обычную ссылку с `rel="nofollow noopener"` и без метки

## Метрика

Счётчик 111249191 вшит в корневой макет. Цели, которые отправляет интерфейс, заведите в кабинете с теми же именами:

| Цель | Когда срабатывает |
|---|---|
| `calc_start` | первое действие в калькуляторе |
| `calc_result` | изменение любого параметра подбора |
| `provider_click` | переход к провайдеру, главная цель, к ней привязываются деньги |
| `catalog_filter` | фильтр или сортировка в каталоге |
| `cookie_accept` | принятие cookie |
| `news_read` | зарезервирована под дочитывание материала |

У цели `provider_click` передаются параметры `provider`, `campaign` и `partner`. Этого достаточно, чтобы в Метрике видеть переходы в разрезе провайдера и страницы

## Проверка перед выкладкой

```bash
npm run build && npm run start
npm run check
```

Скрипт проверяет то, что легко нарушить незаметно при правке текстов: отсутствие темы VPN и обхода блокировок, отсутствие упоминаний оплаты картой и рублями, отсутствие превосходной степени, корректность партнёрских ссылок и атрибутов rel, наличие счётчика, sitemap, канонических адресов и микроразметки

## Три ограничения проекта

Это не рекомендации, а рамки. Нарушение любой ведёт к штрафу, блокировке или отключению партнёрки

1. **Тема VPN на русской версии закрыта полностью.** Ни страниц, ни задач в калькуляторе, ни слова в текстах и тегах. В минус-слова рекламных кампаний добавить обязательно. Для будущей англоязычной версии ограничение не действует
2. **Сайт оформляется как справочный сервис.** Все карточки одинаковые, сортировка по объективным параметрам, комиссия в формулу не входит, в каждом обзоре есть раздел с ограничениями. Как только появится выделение за деньги, потребуются пометка «Реклама», erid, ОРД и отчётность
3. **Брендовый контекст запрещён почти всеми партнёрками.** Рекламные кампании только небрендовые и категорийные. Страницы обзоров провайдеров нельзя рекламировать по брендовым запросам, только органика

## Что осталось сделать вне кода

1. Купить домен и вписать его в `data/site.json`
2. Решить по юридическому лицу: от этого зависят реквизиты оператора на юридических страницах и подача уведомления оператора персональных данных в Роскомнадзор
3. Заполнить `operator` и `contactEmail` в `data/site.json`, они подставятся в политику и на страницу о проекте
4. Получить реферальную ссылку Reg.ru, сейчас провайдер в каталоге без партнёрства
5. Написать парсер цен и переключить `dataStatus` на `live`
6. Отдать юридические страницы юристу на вычитку

## Деплой

Сборка статическая, подойдёт любой хостинг с Node. На Timeweb Cloud минимальный сценарий:

```bash
npm ci
npm run build
npm run start        # или pm2 start npm --name servercalc -- run start
```

Дальше nginx проксирует 80 и 443 на порт 3000, сертификат через Let's Encrypt. Пересборку после работы парсера повесить на cron рядом с ним
